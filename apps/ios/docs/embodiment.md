# Embodiment: the voice ↔ robot interface

How **voice** (the Realtime conversation on the iPhone, `apps/ios`) comes to have a fresh,
truthful picture of what **robot** (the mBot2/CyberPi body, `apps/robot`) is doing — without the
conversation transcript becoming the database, and without voice ever claiming an embodied fact
it does not actually have evidence for.

> **The principle.** Keep authoritative world and action state outside the model. Project
> semantically meaningful transitions, events and snapshots into voice, so every response is
> grounded in a fresh, truthful picture of the body — including the parts voice does *not* know.

This document is the design. `apps/ios/Rocky/Sources/World/` is the implementation.

---

## 1. What exists today, and what breaks

The current flow (before this design):

```
model tool call ──> RealtimeVoiceSession.performToolCall
                      await robot.drive(...)          ← BLOCKS until the board acks completion
                      send function_call_output {"success": true}
                      send response.create
```

Five real faults fall out of that shape:

| # | Fault | Consequence |
| --- | --- | --- |
| 1 | Tool calls block on physical completion | Voice goes silent for the length of the movement. A 6-second drive is 6 seconds of dead air. |
| 2 | `Robot.commandTimeout` is a flat 3s, but `rocky_agent.py` only acks on *completion* | Any drive longer than 3s reports **failure** while the robot is happily driving. A false negative reported to the model as fact. |
| 3 | The tool result is `{"success": true}` | "The command was accepted" is indistinguishable from "the robot moved". The model says "I turned!" because a function returned. |
| 4 | State is **pull-only** (`get_robot_state`) | Between tool calls the model is blind. It has to *remember* to ask, and asking costs a turn. |
| 5 | `BehaviorMonitor.onNotableEvent` → `narrate()` → `response.create` | An unconditional attempt to speak, gated only by a 20s cooldown. No salience judgment; and if a response is already active the Realtime API rejects it outright (`conversation_already_has_active_response`). |

There is also no `action_id` anywhere, so "did *that* work?" is unanswerable, and the session log
is flat text with no correlation identifiers.

Nothing about the two transports is wrong — the newline-JSON motion protocol and the behaviour
loop's event stream both work. What is missing is a **world model between them and the model.**

## 2. Verified Realtime API semantics

Checked against OpenAI's live docs (August 2026), not assumed — every mechanism below is one this
design depends on:

| Mechanism | Verified behaviour |
| --- | --- |
| `conversation.item.create` | Never triggers a response on its own. This is the "teach voice something without making it talk" primitive. |
| Client-settable item `id` | "The unique ID of the item. This may be provided by the client or generated by the server." → we can name our own items and delete them without waiting for a server echo. |
| `conversation.item.delete` | Removes an item from history; server replies `conversation.item.deleted`. → **superseded state can be physically removed**, not just outranked. |
| Out-of-band responses | `response.create` with `response.conversation: "none"` — not added to conversation state, and **may run concurrently** with the in-band response. |
| `response.metadata` | String→string map (keys ≤64, values ≤512), echoed on `response.created`. → our correlation channel for salience judgments. |
| In-band concurrency | Exactly **one** in-band response at a time. A second `response.create` errors with *"Conversation already has an active response"*. → a response gate is mandatory, not optional. |
| `response.cancel` | Optional `response_id`; without it, cancels the active default-conversation response. Passing the id explicitly is the race-safe form. |
| `conversation.item.truncate` | `{item_id, content_index, audio_end_ms}` — drops the server-side transcript of audio the user never heard. |
| `output_audio_buffer.clear` | WebRTC-only client event; stops audio already buffered for playback. Paired server events `output_audio_buffer.started/stopped/cleared`. |

Sources: [Realtime conversations guide](https://developers.openai.com/api/docs/guides/realtime-conversations),
[out-of-band transcription cookbook](https://developers.openai.com/cookbook/examples/realtime_out_of_band_transcription),
[server events reference](https://developers.openai.com/api/reference/resources/realtime/server-events).

## 3. The data model

Three record types and **one sequence space**.

### 3.1 `worldSeq` — the world epoch

A monotonic `UInt64` on the phone, incremented on *every* mutation of the world: a state change, an
event, an action transition. Everything carries the `worldSeq` it was built at: projections, OOB
salience tickets, response ledger entries. This is the single clock that makes staleness decidable.

It is **not** the robot's clock. The board's `utime.ticks_ms()` wraps and is unrelatable to wall
time; board timestamps are carried as opaque debug detail only, never used for ordering.

### 3.2 Robot state — current conditions, last-write-wins

```
<robot-state seq="192">
{
  "body": "here",
  "doing": "spinning",
  "why": "you asked",
  "moving": true,
  "blocked": false,
  "feeling": "excitable",
  "action": { "id": "act_83", "intent": "spin", "status": "running", "sure": true, "for": "2s" },
  "nearest_cm": 24,
  "measured": "3s ago"
}
</robot-state>
```

Rules, stated explicitly because these are the ones that decide whether the model can be trusted:

- **Full snapshots, never patches.** Every `<robot-state>` is a complete picture of the projected
  fields. An omitted field means *"not known, or not applicable"* — it never means "unchanged".
  There is no accumulation to do.
- **The newest `<robot-state>` is the only one that counts**, and the previous one is deleted
  whenever deleting it is free (`conversation.item.delete`, client-assigned ids `rw_state_<seq>`).
  See §4.1 — "free" is doing real work there.
- **Semantic, not telemetric.** `"doing": "spinning"` is what enters voice. Wheel RPM, loudness,
  reflect channels, tick rates stay in the store and the debug log. `speed=.47 → .48 → .46` never
  crosses this boundary at all.
- **`why` separates intent from origin**: `"you asked"` (a voice action), `"on its own"` (the
  autonomous loop chose it), `"reflex"` (a startle/bump/obstacle response nothing chose).
- **`moving` is observed reality, `action.status` is intent.** They are allowed to disagree, and
  that disagreement is the whole point: `intent: drive_forward, status: running, moving: false,
  blocked: true` is what lets voice say *"I'm trying to go forward, but something's in my way"*
  instead of lying.
- **`body`** is link freshness: `"here"` (heard from within 3s), `"quiet"` (3–10s), `"gone"`
  (>10s or socket closed). This is what makes "I've lost track of my body" sayable.
- **Ages are relative and rounded** (`"3s ago"`, `"a while ago"` past 60s). Absolute timestamps are
  meaningless to a model with no clock.

### 3.3 Robot events — durable historical facts

```
<robot-event id="evt_31" seq="193" when="just now">
{ "what": "bumped", "detail": "something touched me", "during": "act_83" }
</robot-event>
```

Stable id, never deleted, never superseded. `during` correlates the event with whatever action was
running, which is what makes *"I tried, but I bumped into something"* a single coherent thought
rather than two facts the model has to join.

The starting vocabulary — deliberately small, and every one of them already exists on the board:

| `what` | Source | Means |
| --- | --- | --- |
| `bumped` | behaviour loop enters `dizzy` | something physically touched the body |
| `startled` | behaviour loop enters `startled` | a sudden loud noise, or something came close |
| `blocked` | motion agent `obstacle stop`, or behaviour loop's obstacle turn | the way ahead is not clear |
| `finished` | action reached `succeeded` | a durable "that one worked" |
| `failed` | action reached `failed` / `lost` | a durable "that one didn't" |
| `body_gone` / `body_back` | link watchdog | contact with the body was lost or regained |

**The state/event boundary rule.** A *terminal* action transition is a durable historical fact →
it becomes an event. A *non-terminal* transition is a current condition → it lives in
`<robot-state>.action` and is superseded like everything else there. One rule, no case analysis.

### 3.4 Actions — lifecycle, with evidence

An action is created the moment the model calls a movement tool, and carries a stable
`action_id` (`act_83`) for its whole life.

```
requested ──> accepted ──> started ──> running ──┬──> succeeded
     │            │            │                 ├──> blocked
     └──> failed  └──> failed  └──> failed       ├──> cancelled
                                                 ├──> superseded
                                                 └──> lost
```

| Status | Meaning |
| --- | --- |
| `requested` | the model asked; nothing has left the phone yet |
| `accepted` | bounded and written to the socket — **the tool result stops here** |
| `started` | the body said it began |
| `running` | believed to be happening now |
| `succeeded` | the body said it finished |
| `failed` | the body refused or errored (`busy`, unknown command, bad args) |
| `blocked` | it began, and something physical stopped it |
| `cancelled` | a stop — from the person, or from voice |
| `superseded` | a newer action on the same channel replaced it |
| `lost` | the deadline passed, or the link died, with no outcome ever heard |

The second axis is the one that makes this honest:

**`evidence: confirmed | assumed | none`.**

The motion agent acks only on *completion*, so between "we wrote the bytes" and "we got an ack"
there is genuinely nothing to know. Rather than invent a `started` we never received, the store
records `status: running, evidence: assumed` — derived from *"we sent it, the link is live, the
estimated duration has not elapsed."* The projection renders that as `"sure": false`, and the
system prompt turns it into *"I've asked my body to turn — I think it's going"* rather than
*"I'm turning."*

The behaviour loop, by contrast, reports its own mode transitions, so a gesture genuinely reaches
`evidence: confirmed`. Same lifecycle, different amount of truth available — and voice can tell
which it has.

`lost` is not `failed`. Failure is something the body told us; lost is something we never learned.
They produce different sentences, and conflating them is exactly how a model ends up asserting a
failure that never happened.

## 4. Projection into voice

`WorldProjector` is the only thing allowed to put robot facts into the conversation.

**What crosses the boundary**

1. **Semantic transitions.** The projector keeps the last-projected snapshot and diffs it against
   the current one on the projected fields only (`body, doing, why, moving, blocked, feeling,
   action.{id,status,sure}`). No semantic change → no projection, however much telemetry moved.
2. **Events**, always — they are rare and each one is a fact worth having.
3. **Checkpoints.** A state snapshot is force-flushed when it is about to matter:
   - on `input_audio_buffer.speech_started` (earliest reliable warning that a response is coming),
   - again on `speech_stopped` if anything changed in between,
   - before any `response.create` we originate,
   - and after ~12s of silence while the body is *not* idle, so a long unbroken motion does not
     drift out of context.

**Coalescing**

- Minimum 700ms between state projections. Changes landing inside that window collapse into one
  snapshot at the end — which is trivially correct because state is last-write-wins by
  construction.
- Transients shorter than 250ms (`settling`, the 180ms motor ring-down) are never projected at
  all; they are machine seams, not things that happened.
- Identical consecutive events inside a 3s window collapse to one with a `"again"` count.

**Delivery**

Every projection is a `conversation.item.create` with `role: "user"`, a client-assigned id, and
one tagged block as `input_text`. The system prompt defines these tags as *your own body sense,
not a person talking* — which is why they are user-role rather than system-role: they are fresh
incoming sensation, not standing rules.

### 4.1 Deleting superseded state without burning the prompt cache

Deletion is the strongest possible form of supersession, and it is not free. Prompt caching is
**exact-prefix**: *"changing, deleting, or reordering earlier content changes the prefix and can
cause a cache miss"*, and the Realtime API is the same — *"any change to the prefix will break the
cache."* So the cost of deleting a state item is exactly **the number of tokens added to the
conversation since it was inserted**:

| Where the item sits | Cost |
| --- | --- |
| Still the last thing in history | Delete + insert is a pure tail operation. The prefix is untouched. **Free.** |
| Conversation has piled on top of it | Everything from its old position onward is a cache miss. |

The second case is not a corner: the projector deliberately *suppresses* projections when nothing
semantic changes, so a robot sitting still through three minutes of conversation leaves its last
snapshot three minutes back — and then one bump would re-charge full price for three minutes of
**audio** tokens to remove eighty tokens of stale JSON. That trade is upside down.

So the policy is:

1. **Delete when it is free.** The projector tracks whether anything has been appended since the
   live snapshot went in (`noteConversationAdvanced`, called generously — over-reporting only
   defers a free deletion, while under-reporting makes the expensive mistake). While nothing has,
   the old item is deleted outright. This is the common case *during motion*, when projections
   cluster a few hundred milliseconds apart, so history stays clean exactly when it churns most.
2. **Otherwise leave it, and let `seq` supersede it.** Every snapshot is whole, so "highest seq
   wins" is a *max*, not a merge — there is still nothing for the model to accumulate. The system
   prompt states this rule rather than the stronger one, because a prompt that promises an
   invariant the system does not guarantee is worse than one that states the real rule.
3. **Sweep in batches, not one at a time.** Once six stale snapshots have accumulated, delete them
   together: the oldest one invalidates everything after it anyway, so the rest come along for
   free. One cache miss instead of six — the same reasoning OpenAI applies to its own context
   truncation, where the fix for repeated cache-busting was to truncate *harder, less often*.

The system prompt sits at position 0 and nothing is ever deleted before it, so the largest single
cached block is never at risk.

**And it is measured, not argued about.** `response.done` carries
`usage.input_token_details.cached_tokens`, so every response now records its cached share into
`world.jsonl` and onto its ledger card in the Body panel. A cached percentage that collapses
directly under a projection is this design's bill arriving, visible in the same view as the
projection that caused it. The threshold of six is a guess in exactly the sense every constant in
`rocky_behavior.py` is a guess — and now it is one with an instrument pointed at it.

## 5. Salience: cognition vs speech

Two questions, deliberately answered by different machinery:

> **Should this affect what voice knows?** — almost always yes; projection is cheap and already coalesced.
>
> **Should this interrupt speech right now?** — rarely, and never by accident.

`SalienceVerdict`: `ignore | context | afterUtterance | interrupt | urgent`.

### 5.1 Deterministic tier — immediate, no model in the loop

Safety and self-contradiction never wait on an LLM round trip:

| Condition | Verdict |
| --- | --- |
| A stop was commanded, or the body stopped itself for an obstacle **while voice is asserting motion** | `urgent` |
| `bumped` / `startled` while voice is speaking | `interrupt` |
| An action voice announced reached `blocked` / `failed` / `lost` while voice is speaking | `interrupt` |
| Voice is silent and the event is notable | `interrupt` (a fresh response — nothing to cut off) |
| Any other state change | `context` |
| A duplicate inside its cooldown, or pure telemetry | `ignore` |

Rate limits: at most one speech interruption per 8s, and never two consecutive interruptions for
the same event kind. A robot being bumped repeatedly must not become a commentator.

### 5.2 Judged tier — out-of-band, for the ambiguous middle

Anything not resolved above and arriving *while a response is generating* goes to the model
itself, out of band, text-only:

```json
{ "type": "response.create",
  "response": {
    "conversation": "none",
    "output_modalities": ["text"],
    "metadata": { "purpose": "salience", "ticket": "sal_9", "seq": "193" },
    "instructions": "<judge prompt: strict JSON verdict + reason>",
    "input": [ { "type": "message", "role": "user",
                 "content": [ { "type": "input_text", "text": "<what she is saying right now> / <what just happened>" } ] } ]
  } }
```

It carries no tools, writes nothing to history, and cannot move the robot. The utterance-so-far is
**inlined** rather than referenced by `item_reference`, so the judge never depends on the state of
a server-side item that may be cancelled underneath it.

Returns `{"decision": ..., "reason": "..."}`. Runtime consumes the enum; the reason is kept for the
debug log, verbatim.

### 5.3 Race safety

Every judgment carries a `SalienceTicket`:

```
ticketId · eventId · forResponseId · worldSeq · issuedAt
```

A returning verdict is **discarded** if any of these is true:

- `forResponseId` is not the currently-generating response (it was cancelled, or finished),
- the ticket has been superseded by a later one,
- `worldSeq` is older than the newest already-judged seq,
- the event has already been resolved by the deterministic tier.

Which settles the scenario from the brief exactly: R17 speaking → event A judged → event B cancels
R17 → R18 begins → A returns CONTINUE → **`forResponseId` is R17, R17 is not current, dropped.**

**One superseding slot, not many independent judgments.** The question being asked is *"does what
just happened invalidate what she is saying right now?"* — that question has exactly one current
answer. A new event while a judgment is in flight supersedes the old ticket and re-asks about the
latest world change (noting that several things happened). This bounds cost and latency, and
removes "two verdicts disagree" as a state that can exist. The deterministic tier remains
per-event and instant, so safety is never behind this queue.

## 6. Realtime orchestration

### 6.1 The response gate

One in-band response may exist at a time, so `RealtimeVoiceSession` gets a single
`pendingResponseRequest` slot. Any request to speak while a response is active is parked, and
fires on `response.done`/`response.cancelled`. Newer parked requests replace older ones. This also
fixes the pre-existing collision between a tool-call follow-up and `narrate()`.

### 6.2 Interruption, in order

```
verdict interrupt/urgent
  ↓ response.cancel { response_id }        ← the specific response, not "whatever is current"
  ↓ output_audio_buffer.clear              ← WebRTC buffered playback
  ↓ stopLocalAudio() + hume.cancel()       ← the Hume path plays outside WebRTC entirely
  ↓ conversation.item.truncate { item_id, content_index: 0, audio_end_ms }
  ↓ project the event (+ a fresh state snapshot)
  ↓ response.create { instructions: react to it, past tense, no machinery words }
```

`audio_end_ms` is measured from `output_audio_buffer.started` for the model-voiced path, and read
off `HumePcmPlayer` for the Hume path (where it is exact). The assistant `item_id` comes from
`response.output_item.added`. If no item id was seen, truncation is skipped — cancelling alone
already prevents the ungenerated remainder from existing.

### 6.3 Tool calls return immediately

```
model tool call ──> register action (status: accepted, evidence: none)
                    write to the socket
                    return { "action_id": "act_83", "status": "accepted" }   ← no physical claim
                    (no response.create — the projection of the *real* transition is what speaks)
```

`read_distance` stays synchronous: it is a query, it is fast, and the answer is the point.
`get_robot_state` returns the same projected snapshot the pushed state uses — one abstraction,
two delivery routes.

## 7. The two vocabularies

Voice must never emit machinery language. The prompt gets an explicit translation table rather
than a general instruction, because "don't be technical" has repeatedly not been enough:

| Never say | Say |
| --- | --- |
| collision, collided | "oof — I bumped into something" |
| obstacle, blocked | "something's in my way" |
| action, command, request, tool, queue | *(nothing — just move and keep talking)* |
| accepted, queued, pending | "I've told my body to" / *(nothing)* |
| started, running, in progress | "I'm doing it now" |
| succeeded, completed | "that's done" |
| failed, error | "that didn't work" / "I couldn't" |
| cancelled, superseded | "I stopped that and did the other thing instead" |
| stale, timeout, no confirmation | "I asked, but I haven't felt it happen yet" |
| state, snapshot, sequence, event, status | *(never)* |

Paired with the epistemic phrasebook — the sentences that must be *available*:

- accepted, not started → *"I've told my body to turn, but it hasn't gone yet."*
- running, confirmed → *"I'm turning right now."*
- running, assumed → *"I should be turning — I can't feel it yet."*
- succeeded a while ago → *"That finished a few seconds ago."*
- blocked → *"I tried, but something's in the way."*
- lost → *"I sent it, but I've lost track of my body."*

## 8. Debugging and observability

### 8.1 `WorldLog` — one structured stream

JSONL to `Documents/world.jsonl`, pulled with the same `devicectl` route as `session.log` (and
added to `apps/ios/scripts/pull-log.sh`, so the coding agent gets it too). Every record:

```json
{"t":"2026-08-16T12:00:03.412Z","seq":193,"lane":"event","event_id":"evt_31",
 "action_id":"act_83","response_id":"resp_abc","note":"bumped during act_83","detail":{…}}
```

Lanes: `state · event · action · projection · salience · response · tool · link`.

### 8.2 The response ledger — "what did the model know?"

On every `response.created`, one record is written answering the question the brief asks for
directly:

```
Response resp_abc  (R41)
  began at world_seq   192
  active action        act_83  spin  running (assumed)
  most recent event    evt_31  bumped  2s ago
  live state item      rw_state_192   "spinning · you asked · moving"
  superseded since     rw_state_188, rw_state_190
```

### 8.3 The in-app panel

A **Body** sheet behind the existing state chip: a merged, time-ordered timeline colour-coded by
lane (a true multi-column swimlane is unreadable on a phone), with correlation-id chips
(`act_83`, `evt_31`, `resp_…`) that filter the timeline when tapped. Superseded state rows render
dimmed and struck through, so "this is no longer what voice believes" is visible at a glance. Tap
a response row to see its ledger entry.

## 9. Scenario walkthrough

For each: **(1)** canonical state · **(2)** what voice is shown · **(3)** generate / interrupt /
reconsider · **(4)** the natural line.

| # | Scenario | Canonical | Projected to voice | Speech decision | Ideal line |
| --- | --- | --- | --- | --- | --- |
| 1 | Asked to spin, not started yet | `act_83 accepted, evidence none` | state: `doing: still, action{spin, accepted, sure:false}` | none (tool result is silent) | *"Okay — hang on."* / if asked: *"I've told my body to spin, it hasn't gone yet."* |
| 2 | Spin running | `act_83 running, confirmed` | state: `doing: spinning, why: you asked, moving: true, action{running, sure:true}` | `context` | *"Are you doing it?"* → *"I'm spinning right now!"* |
| 3 | Spin succeeded | `act_83 succeeded` + `evt finished` | state (action cleared) + event | `context` | *"Did you do it?"* → *"Yep, all done — I'm dizzy."* |
| 4 | Failed before starting (`busy`) | `act_83 failed(busy)` | state + `evt failed` | `context` (silent) or `interrupt` if she announced it | *"I couldn't — my body was already doing something."* |
| 5 | Interrupted midway | `act_83 cancelled`, `act_84 accepted` | state + `evt` | `interrupt` if she was asserting the spin | *"Oh — I stopped."* |
| 6 | Physically blocked | `act_85 blocked` | state: `moving:false, blocked:true` + `evt blocked` | `urgent` if she claimed motion | *"I'm trying to go forward, but something's in my way."* |
| 7 | Superseded by a new command | `act_83 superseded`, `act_86 accepted` | one state snapshot showing only `act_86` | `context` | *"Never mind that — doing this instead."* |
| 8 | Event while speaking | mid-utterance `bumped` | judge OOB → `interrupt` | cancel → clear → truncate → new response | *"— oof! Something bumped me."* |
| 9 | Event while silent | `startled` | deterministic `interrupt` (nothing to cut) | fresh response | *"Whoa. Something loud."* |
| 10 | Several events in a burst | 3 events in 400ms | coalesced: one state + the newest event with `again: 3` | one interruption | *"Hey — stop poking me!"* |
| 11 | Two judgments race | tickets `sal_9`, `sal_10` | — | `sal_9` superseded on issue; only `sal_10` can act | (nothing visible — that is the point) |
| 12 | Stale verdict arrives | `sal_9` for `resp_R17`, now on `R18` | — | dropped: `forResponseId` mismatch | (nothing) |
| 13 | State changed many times before voice speaks again | 9 transitions | the newest `<robot-state>`; predecessors deleted where free, otherwise outranked by `seq` | none | *"I've been rolling around a bit."* |
| 14 | Contact lost | link watchdog | state: `body: "gone"`, action → `lost` + `evt body_gone` | `interrupt` if an action was live | *"I've lost track of my body — I can't feel it."* |
| 15 | Says running, sensors say still | `running(assumed)` + `moving:false` | both fields, disagreeing, unedited | `context` | *"I'm trying to move — but I don't think I'm going anywhere."* |

Scenario 15 is the reason `moving` is a separate field from `action.status` and not derived from it.

## 10. Device-side changes

Small, additive, and none of them touch a tuned constant (`check-behavior-parity.mjs` stays green).

**`rocky_agent.py`** — send `{"type":"started","id":…}` when a drive/turn begins, so a motion-agent
action can reach `evidence: confirmed` instead of being assumed for its whole duration. Completion
acks and the `obstacle stop` error are unchanged.

**`rocky_behavior.py`** — carry detail through transitions that currently have none, so the event
stream says *what happened* rather than only *which mode was entered*: `startled` gains
`"loud noise"` vs `"something came close"`, the obstacle turn gains `"obstacle"`, and gesture
intents carry an optional client `id` echoed in the ack and in the transition detail, so a
gesture's lifecycle is genuinely correlatable rather than inferred by timing.

**Client side** — `Robot.commandTimeout` splits into an *acceptance* deadline (~1.5s, for
`started`/immediate ack) and a *completion* deadline scaled to the estimated duration. Expiry of
the completion deadline yields `lost`, not `failed`.

## 11. Shape of the implementation

```
apps/ios/Rocky/Sources/World/
  WorldModel.swift       — value types: WorldSnapshot, WorldEvent, RobotAction, Evidence, verdicts
  WorldStore.swift       — the authoritative store; owns worldSeq; the only writer
  WorldProjector.swift   — diff, coalesce, supersede, deliver; owns conversation item ids
  SalienceJudge.swift    — deterministic rules + OOB tickets + race guards
  WorldLog.swift         — structured JSONL + the response ledger
  WorldSources.swift     — adapters: motion agent → store, behaviour loop → store
```

Only one payload runs on the board at a time, so the two adapters are alternatives, never both —
same fact `BehaviorMonitor`'s single sweep already encodes. `RealtimeVoiceSession` keeps its
existing turn timing, watchdogs and audio handling, and gains the response gate and the
projection/salience wiring.
